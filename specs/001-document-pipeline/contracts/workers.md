# DM-02 recoverable workers — 2026-11-02

Scope: T006/T007, DM-A04–A06 queue semantics. General document parsing, PDF, live AI, semantic extraction validation and full result/retry UI stay in DM-03/DM-04. No paid services. Implement against issue #3 on a feature branch.

- W01: one atomic claim per eligible job using PostgreSQL row locking and SKIP LOCKED, with a fresh random claim token each time. Commit before processor I/O. Ready jobs and expired leases are eligible; active leases and future retry times are not. Count every claim, including crash recovery, toward three total attempts.
- W02: default lease 30 seconds, heartbeat every 10 seconds, attempt deadline 60 seconds, polling every second. PostgreSQL wall-clock time determines eligibility/fencing; heartbeat cannot extend past the attempt deadline. Queue operations have a five-second timeout. Processing stops before the hard deadline by min(5 seconds, attempt duration / 5), leaving time for fenced finalization. Test configurations use shorter durations without changing production defaults.
- W03: only the current token, processing state and unexpired lease/deadline can renew, complete or fail. Lock the row before checking wall-clock validity to reject workers that waited past expiry. Stale operations return a distinct lost-claim error and never mutate the current job/result. State and result insertion commit atomically; duplicate completion cannot insert a second result. A crash on the third attempt eventually becomes failed, not an infinite processing loop.
- W04: typed transient failure schedules retry_wait: 5 seconds then 30 seconds plus up to 20% positive jitter. A supplied Retry-After increases the delay but is capped at 60 seconds. A third failure becomes failed; permanent/invalid-result failures stop immediately. Persist only allowlisted error codes, never raw errors. Retry-After and error classification are adapter contracts; no live 429/provider call is claimed here.
- W05: processors must honor cancellation. On heartbeat loss cancel processing, and on SIGTERM stop claiming/cancel the in-flight processor; leave the claim for lease recovery rather than falsely succeeding. A successful processor outcome must have a bounded version-1 result structure and provenance before entering the transaction. Full excerpt/source and provider-payload validation remain DM-03.
- W06: worker --check remains read-only. Normal invocation without a configured extractor refuses to consume work. An explicit --smoke-document ID activates a diagnostic processor restricted to that exact document and content beginning `DOCUMIND WORKER SMOKE\n`; it stores an unmistakably synthetic result with provider `diagnostic`, model `worker-smoke-v1`. This is not the DM-03 fake extraction adapter. Smoke CLI flags can inject bounded delay or transient/permanent failures for that selected fixture only. No hidden development authentication bypass.
- W07: list/detail return real status, attempts and safe error code. UI displays those actual values after Refresh documents; it must not label every state Queued. It does not claim automatic polling, result viewing or manual retry implementation. Retry of active work remains 409 job_active; terminal work returns 409 retry_not_enabled until DM-04.

Evidence: real PostgreSQL concurrent claims, skip-locked behavior, expired/future eligibility, renew/deadline cap, stale renew/fail/complete including lock-wait expiry, one atomic result, malformed result rejection, transient/permanent failures, backoff limits, exhausted crash recovery, and SIGKILL/SIGTERM of real worker processes followed by restart. Synthetic S3 upload smoke verifies persisted processing/success and exact source privacy; browser checks show actual state without claiming AI. Tests isolate their own document IDs so existing uploads are never consumed. Existing migrations remain checksum-identical.
